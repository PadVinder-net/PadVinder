# AGENTS.md

Guidance for AI agents and human contributors working in this repository.

PadVinder is a mobile web app (PWA) plus a web portal for volunteer groups that help amphibians cross roads during the spring migration ("paddentrek") and that monitor street drains for trapped animals ("Pad uit de put"). Volunteers count animals in the field; coordinators and admins manage routes, drains and species; reports follow directly from the counts. The first user is Paddentrek Enschede. See `README.md` (Dutch) for the public description.

This file summarizes the technical chapter (section 16) of the project plan of 20 November 2026. The plan itself is in Dutch and is not in this repository. When the plan and this file disagree, ask the maintainer.

## Language

- **Code is English:** identifiers, file names, database tables and columns, API paths and fields, comments, tests, commit messages, pull requests and technical documentation. Use American spelling (`organization`, `color`).
- **Everything a user reads is Dutch:** UI copy, emails, push notifications, validation messages, export column headers. The app is Dutch-only; there is no translation layer and no i18n library. Write Dutch copy inline.
- **URL paths are English,** also for pages a user sees in the address bar: `/transects`, not `/trajecten`.
- **Domain terms** come from the Dutch project plan. Use the English identifier from the glossary below in code, and the Dutch term in UI copy, exactly as listed. Do not invent a second translation for the same concept. If a concept is missing, add it to the glossary in the same pull request.
- `README.md` stays in Dutch: it addresses volunteers and the public.

### Dutch copy

- Address the user informally with "je", never "u".
- Write short, active sentences in plain words. Readers range from children to pensioners, and they read on a phone, outdoors, in the evening.
- Use the Dutch glossary terms exactly; do not vary them ("traject" stays "traject", not "route" or "pad").
- Avoid English and technical jargon. Say what the user can do next, not what went wrong inside the system.
- Use sentence case for buttons and headings: "Open je mail", "Werk de app bij".

Each app is meant to be built separately; `pnpm release:build` bundles all four into one release (see "Release").

## Constraints behind these choices

Weigh every new dependency or service against these:

- **Running costs stay very low.** The target is under € 200 per year; the current design costs about € 70–75.
- **No vendor lock-in.** Everything runs as plain Linux processes against a standard PostgreSQL. Moving to another host must stay a matter of dump and restore, copying files and changing DNS. Do not use provider-specific features.
- **As little third-party SaaS as possible** inside the application, unless it is free. Prefer building it into our own backend and database. No Firebase, no Redis, no hosted auth.
- **Mainstream, debuggable technology.** Most code is written by AI; humans and agents must be able to debug it with the browser tools and `curl`.
- **Data stays in the EU.**
- **Phone only** for the mobile app. No tablet or desktop layouts there.

## Architecture rules

### Data integrity

- **Never lose or double-count a registration.** The app buffers registrations locally and resends them after a short connection drop, so every write from the field (a tap, an observation, a round, a drain check) must be idempotent.
- **The client generates the ID, as a UUIDv7.** That ID is the record's primary key and its idempotency key: the app creates it once, when the user acts, and sends the same ID on every resend. A `POST` with an ID the server already has returns the stored record and changes nothing. The server never replaces a client-generated ID with one of its own.
- **There is no offline mode.** The app needs a connection. Buffering covers brief interruptions only. Do not build sync or conflict resolution, and do not make design choices that would rule out offline registration later.
- **Effort is always recorded.** A round without observations and an empty drain check are stored like any other. "Nothing found" must stay distinguishable from "not checked".
- **Check status is derived, never stored as user input.** It follows from the latest round, drain check or bucket count. A round in progress shows as "being walked now", with start time and who. A round without activity is closed automatically by a background job.
- **Transects, drains and buckets behave alike.** All three have a check status and appear in the same lists and on the same map.
- **Corrections keep history.** The original registration stays traceable. An audit log records who changed or approved what.
- **Missing values in imported data stay `unknown`.** Never fill them with assumptions.

### Time

- **The time of an action is not the time it arrived.** A buffered registration reaches the server later than it happened. The client records when the user acted (for example `observedAt`, `startedAt`) and sends it along; the server separately records when it received the request (`receivedAt`). Reports and check status use the time of the action. Keep both, so a wrong phone clock can be detected.
- **Do not read the time from the UUIDv7.** It is an ID, not a field.
- **Store every moment as `timestamptz`,** and send it over the API as ISO 8601 with an offset.
- **Day boundaries use Europe/Amsterdam,** never the server's time zone: "up to and including yesterday", scheduled jobs, and time blocks that depend on sunset.

### Location and geometry

- **Store all geometry in WGS84 (EPSG:4326).** The API, GeoJSON and MapLibre use the same.
- **Coordinate order is longitude, latitude,** as in GeoJSON, PostGIS and MapLibre. Never pass a bare number pair around: use GeoJSON or named `longitude` and `latitude` fields.
- **Distances and lengths are in meters.** Compute them on the PostGIS `geography` type or in a projected coordinate system, never in degrees.
- **Store the GPS accuracy in meters** with every position, as the device reports it.
- **Imports state their source coordinate system explicitly.** It is not yet known in which coordinate system the municipality's drain data arrives; Dutch government data is often in RD New (EPSG:28992). The importer reads the coordinate system from the file where the format carries it, otherwise requires it as input, transforms to WGS84, and checks that the result is plausible before saving. Never guess the coordinate system from the values.

### Multi-tenancy, permissions and privacy

- **Organizations are strictly separated:** PadVinder → organization → working group → transects and volunteers. Scope every query by organization; the species list is the one exception (see "Species"). A volunteer can belong to several working groups.
- **Role and view mode are separate.** The role and the safety clearance decide what a user may do; the view mode only changes how the input screen looks. Never use the view mode for authorization.
- **Enforce permissions on the server,** per row and per field. Risky actions on drains require a valid safety clearance.
- **Who sees names** (decided by the maintainer on 21 November 2026):
  - Fellow members of a shared working group see your name and role, nothing else.
  - Coordinators of that group and admins of that organization see your name, email address and phone number.
  - A coordinator and the organization's admins see the same of someone with a pending membership request to their group.
  - Platform admins see everything.
  - Names never appear in an export or download, for any role.
- **Not public:** drains, buckets, exact locations of observations, and personal data. Public pages show transects and aggregated numbers only.
- **Photos are private until moderated.** Strip metadata and GPS from photos that become public.
- **Collect minimal personal data:** name, email (required), phone (optional), working group. No address, no date of birth. Children have no accounts.
- **Location:** GPS per observation and per drain check, in the foreground, after explicit consent. Never record a walked track, and never use location in the background.
- **This repository is public.** Never commit secrets, real personal data, or real locations of drains, buckets or observations. Fixtures and seed data are made up.

### Roles and permissions

The design is `docs/superpowers/specs/2026-11-21-accounts-and-access-design.md` ("Who is who", "Permissions").

- **How roles are stored.** An account is global; it belongs to the person, not to an organization. A `volunteer` is a row in `working_group_memberships`; a `coordinator` is such a row with `is_coordinator` set (a coordinator is a volunteer too, so it is a flag, not a role column), `organizationAdmin` is a row in `organization_admins`, `platformAdmin` is the flag `users.is_platform_admin`. A logged-in user with none of these is an applicant. There is no "current organization" in a session: a request names the working group or record it is about. Everything is read from the database on each request (`getAccess` in `packages/db/src/access.ts`); memberships of inactive working groups do not count.
- **The permission module.** Reference: `apps/api/src/permissions/rules.ts`. A route that needs a login has `preHandler: app.requireActor`, which sets `request.actor` (`Actor`: `userId`, `user` (the profile, read with the session), `isPlatformAdmin`, `memberships`, `adminOfOrganizationIds`). Routes reach the user only through `request.actor` and decide only through `authorize(actor, permission)` (throws the right error) or `decide(actor, permission)` (returns `allowed`, `forbidden` or `hidden`). A route that compares a role itself is a defect. To add a rule, add a member to the `Permission` union and a case in `decide`; a missing case is a type error. "Of the group" and "of the organization" are literal: a coordinator of another group or an admin of another organization is an outsider. The organization is a target too: `organizationRelationTo(actor, { organizationId })` gives `platformAdmin`, `organizationAdmin` or `outsider`, and a member or coordinator of one of its working groups is an outsider to the organization (404). `organization.view`, `organization.changeContact` and `organization.createWorkingGroup` are for its admins and platform admins; `organization.rename` and `organization.manageAdmins` for platform admins only (403 for its admins); `platform.manageOrganizations` adds organizations. `organization.readAuditLog` is for its admins and platform admins; `platform.managePlatformAdmins` and `platform.deleteAccounts` for platform admins only. `workingGroup.manage` (name, city, on and off) and `workingGroup.setCoordinator` are for admins of the group's organization and platform admins; its coordinators and volunteers get 403.
- **The 401, 403 and 404 rule.** 401 `not_logged_in` without a login; 404 `not_found` for a record the actor may not see at all, including everything in another organization, so its existence does not leak; 403 `not_allowed` for a record the actor may see but not change.
- **A decision made on the coordinator flag is checked again when it is applied.** Approving a request adds a volunteer membership (`isCoordinator` false) and keeps one the user has already. Removing a member (`DELETE /api/memberships/{id}`) decides `workingGroup.removeMember` on the flag it loaded, and the delete only goes through while the flag still has that value (`expectedIsCoordinator` in `removeMembership`); otherwise it answers 409 `membership_changed`, so a coordinator never removes someone who was made coordinator in the meantime.
- **Platform admins are made only through the administration functions** in `packages/db/src/admin.ts` (`grantPlatformAdmin`, `revokePlatformAdmin`, and `removePlatformAdmin`, which takes a user ID, for the portal). Every writer of `users.is_platform_admin` must go through them: they take the advisory lock that protects "the last platform admin" from two concurrent revokes. A revoke needs another platform admin who has logged in at least once (`email_verified`), so an account the tool made for a mistyped address does not count. Account deletion (`deleteAccount` in `packages/db/src/accounts.ts`) takes the same lock and applies the same rule. The portal's page Hoofdbeheerders uses `GET` and `POST /api/platform-admins` (the address in the body; `grantPlatformAdmin`) and `DELETE /api/platform-admins/{userId}` (`removePlatformAdmin`; 404 for someone who is no platform admin). A platform admin may remove themself while another platform admin who has logged in remains; the page answers `last_platform_admin` with "Er moet een hoofdbeheerder blijven die al eens is ingelogd."
- **An organization always has an admin, and an active working group a coordinator.** `createOrganization` and `createWorkingGroup` (`packages/db/src/admin.ts`) make the first admin or coordinator in the same transaction. Taking away the last admin (`removeOrganizationAdmin`, `revokeOrganizationAdmin`) is 409 `last_organization_admin`; taking away the last coordinator of an active group (`setCoordinator`, `revokeCoordinator`, and `removeMembership` behind `DELETE /api/memberships/{id}`) is 409 `last_coordinator`; switching on a group without a coordinator is 409 `no_coordinator`. An inactive group may be without a coordinator, and someone can be made coordinator while it is off (`setCoordinator`; the tool's `grantCoordinator` refuses an inactive group). An admin or coordinator who never logged in counts; a deleted account does not (`countOrganizationAdmins`, `countCoordinators`). Account deletion refuses the last one too (see "Deleted accounts are soft-deleted").
- **Who may be a first coordinator.** When a user names the first coordinator of a new working group, the address may be their own; one without an account, or whose account never logged in; that of a member of any working group of the organization, active or not; or that of an admin of the organization. Anyone else has a profile outside the organization: 409 `person_outside_organization` (`assertMayNameFirstCoordinator`), so nobody pulls a person from another organization into theirs. The administration tool (the system) may name anyone.
- **Whether someone ever logged in** is decided by `users.last_login_at` for member lists, for `hasLoggedIn`, for who may be a first coordinator and for whether adding by address adds or invites (see "Adding people"), never by the name. It is set on every login by `databaseHooks.session.create.after` in `apps/api/src/auth/auth.ts` and read with `userHasLoggedIn` (`packages/db/src/users.ts`); responses show it as `hasLoggedIn`, the portal as "(nog niet ingelogd)". For accounts that existed before the column, the migration `backfill_last_login_at` filled it from their newest session, or from `updated_at` for a verified account without one (Better Auth deletes the session on logging out); an unused or deleted account kept null. The rule on the last platform admin (`hasOtherPlatformAdmin`) still reads `email_verified`, which a first login sets.
- **Locks for the last admin and coordinator.** `lockOrganization` and `lockWorkingGroup` (`packages/db/src/admin.ts`) lock the row `for no key update`, so inserts that reference it (an admin row, a working group, a membership, a request) do not wait. Every function that removes an admin row takes the organization's lock before it counts the admins; every function that removes a membership, clears the coordinator flag or changes `active` takes the group's lock before it counts the coordinators, and reads what it checks again under the lock. A function that needs several takes organizations before working groups, each in the order of their IDs. `deleteAccount` takes, in this order: the platform admin lock, the user's request lock, the user's pending request rows, the organizations they administer, the working groups they are a member of, then the user row; then it reads the roles again and locks any that appeared in between. `addMemberByEmail` takes them in the same order: the request lock of the account with the address and its pending request rows for the group, the working group, then the user row. `findOrCreateUser` (every grant by address, and adding by address) holds an existing user row `for key share`, so a grant that races a deletion either commits first, and the deletion counts the role, or waits and answers `user_not_found`.
- **The audit log.** `recordAudit(tx, entry)` in `packages/db/src/audit-log.ts` writes one row of `audit_log_entries`. It takes the transaction that makes the change, like `notify`, so an entry exists exactly when the change was committed. Record an entry when one person decides or changes something about another person or about shared data (roles, memberships, organizations, working groups, species, decided requests, deleted accounts); a person's own registrations, views and logins are not audit entries. `details` holds which fields changed and non-personal values (a role, a status), never a name of a person, an email address or a phone number: people appear by ID only. `recordAudit` rejects every key that contains `name`, `mail` or `phone` in any case, such as `fullName`, except the exact keys in `THING_NAME_AUDIT_KEYS` (same file), which hold the name of a thing (`dutchName`, `organizationNameFrom`, `workingGroupNameTo` and the like: a species, an organization or a working group), never of a person; add a key there only for that. It rejects every text value with an `@`, also under those keys. The administration actions are `organization.created`, `organization.updated` (`organizationNameFrom`/`To`, and `contactChanged: true`: the contact address itself is never in the log), `working_group.created`, `working_group.updated` (`workingGroupNameFrom`/`To` and `cityFrom`/`To`, only for what changed), `working_group.deactivated`, `working_group.activated`, the `role.*` grants and revokes, and `membership.added` and `membership.invited` (adding by address: the person as subject, details `{ workingGroupId }`, never the address); a save that changes nothing writes no entry. The administration tool writes entries with the actor `system`. The database rejects `UPDATE`, `DELETE` and `TRUNCATE` on the table.
- **Reading the audit log.** The actions are `auditActions` in `packages/contracts/src/audit-log.ts`. A new action needs its sentence in `sentences` in `packages/ui/src/lib/audit-log.ts` (a type error until then; an action an open portal does not know yet reads as its own text, such as `safety_test.published`), and falls into a filter group of `auditActionPrefixes` by its prefix (the page's Actie: Organisaties, Werkgroepen, Rollen, Leden en aanmeldingen, Accounts, Soorten; an organization admin's Actie has the first four groups only, without Accounts and Soorten, `organizationAdminActionGroups` in `apps/portal/src/pages/audit-log-page.tsx`). `listAuditLogEntries` (`packages/db/src/audit-log-entries.ts`) is the one reader, behind `GET /api/audit-log-entries` (`apps/api/src/routes/audit-log.ts`; query `organizationId`, `actionGroup` and `cursor`), and it is scoped by organization: a platform admin reads every entry, an organization admin the entries of the organizations they administer (never one without an organization, such as `account.deleted` and the species), anyone else an empty page; a filter on an organization the actor may not read is 404. An entry carries the current names of the organization, working group and species it is about. Who acted and whom it is about are `named` (the current name and `hasLoggedIn`) for a platform admin; for an organization admin only someone connected to the entry's own organization now (a membership of one of its working groups, also one switched off, a pending request for one, or an admin row of it). Anyone else is one of four fixed texts (the kinds of `AuditLogPerson`, shown by `auditLogPersonName` in `packages/ui`): "Systeem" (`system`, the administration tool), "Verwijderd account" (`deleted_account`), "Hoofdbeheerder" (`platform_admin`, a platform admin who is not connected) and "Voormalig lid" (`former_member`). An answer holds no email address, no phone number and no user ID; the API tests check the raw JSON. The page does not follow live events; it loads again when it is opened.
- **Deleted accounts are soft-deleted.** `deleteAccount` in `packages/db/src/accounts.ts` keeps the row in `users`, with the name "Verwijderd account" (`DELETED_ACCOUNT_NAME`), the address `deleted-<id>@deleted.invalid`, no phone, no platform admin flag and `deleted_at` set; it removes the sessions, memberships and admin rows and withdraws pending requests. Everything that points at the user stays: decided requests now, rounds and drain checks later. It cannot be undone; the same address later logs in as a new account. It refuses the only coordinator of an active working group and the only admin of an organization (`{ outcome: "blocked", blockers }`, one per group and organization; nothing changes, and `DELETE /api/me` answers 409, see "API and versioning"); a second one who never logged in is enough. `deletedBy` names the actor of the `account.deleted` entry when someone else deletes the account (default: the user). With `onlyIfUnused` it deletes only an account nobody uses yet, and otherwise answers `kept` and changes nothing: it keeps an account that has logged in or is verified (a first login in progress), or that has a membership, an admin row, a pending request or the platform admin flag. A platform admin deletes someone else's account on the page Account verwijderen: `POST /api/users/lookup` (`findAccountByEmail`, same file) finds the account by its whole address, and `DELETE /api/users/{userId}` (`apps/api/src/routes/users.ts`) calls `deleteAccount` with the platform admin as `deletedBy`. It obeys the same blockers as `DELETE /api/me` (409 with `blockers`, and `last_platform_admin`), answers 404 for an account that is gone, and refuses the actor's own account (409 `own_account`: that goes through the app, which also ends the session). Every query that lists people, loads access or chooses mail recipients skips users with `deleted_at` (`isNull(users.deletedAt)`), and a response about a deleted person leaves out the `email` and `phone` keys.
- **The working group list is the one response that crosses organizations.** `GET /api/working-groups` (`listWorkingGroupDirectory` in `packages/db/src/working-groups.ts`) gives every logged-in user every active working group with exactly its name, its organization's name and its city. Never add a field to it: no coordinators, no member counts.

### Organizations and working groups

The design is `docs/superpowers/specs/2026-11-22-portal-administration-design.md` ("Organizations and working groups", "API"). The functions are in `packages/db/src/admin.ts`, `organizations.ts` and `managed-working-groups.ts`; the routes in `apps/api/src/routes/organizations.ts`, `working-groups.ts` and `memberships.ts`; the pages in `apps/portal/src/pages/`.

- **Endpoints.** `GET /api/organizations` (the organizations the actor administers: all for a platform admin), `GET`, `PATCH /api/organizations/{id}` (name, `contactEmail`), `POST /api/organizations` (with `adminEmail`, optional `contactEmail`), `POST /api/organizations/{id}/admins`, `DELETE /api/organizations/{id}/admins/{userId}`, `POST /api/organizations/{id}/working-groups` (with `coordinatorEmail`), `GET /api/managed-working-groups` (the groups the actor manages: all for a platform admin, every group of the organizations they administer, the active groups they coordinate; with member and pending request counts), `PATCH /api/working-groups/{id}` (name, city, `active`), `PATCH /api/memberships/{id}` (`isCoordinator`) and `POST /api/working-groups/{id}/members` (see "Adding people"). The server makes every ID: this is administration, not a write from the field.
- **Names.** Names and cities are trimmed with spaces collapsed (`normalizeName`). Organization names are unique ignoring capitals (`organizations_name_key` on `lower(name)`), working group names per organization (`working_groups_name_key` on `(organization_id, lower(name))`); a taken name, also from a create at the same moment, is 409 `name_taken` with `issues[0].path` `name`. A name or a city may not contain `@` (400), because the audit entry holds it.
- **Nothing is deleted.** Organizations and working groups have no delete. A working group is switched off with `active: false`: its memberships give no rights (`getAccess`), its members lose it from `/api/me` (the app shows the picker to someone for whom it was the only group), and switching it on gives it back; both send `access-changed` to every member. A rename sends no event.
- **The contact address** (`organizations.contact_email`, optional) is what the app tells a member to write to, for example when they cannot delete their account. Its admins and platform admins change it; the audit entry says only `contactChanged`.
- **The portal** asks the API, never decides itself: `useManagedWorkingGroups`, `useOrganizations`, `useOrganization` and the mutations in `packages/api-client/src/administration.ts` refetch the administration queries and me after every change, and `useAccessLiveUpdates` refetches them (`refetchAdministration`) on `access-changed`, on `membership-requests-changed` and when the event stream (re)opens. `mayManageWorkingGroup` and `administersOrganization` there only decide which buttons show. A list that loaded keeps showing when a refetch fails.

### Adding people

The design is `docs/superpowers/specs/2026-11-22-portal-administration-design.md` ("People", "The mail queue"). The function is `addMemberByEmail` in `packages/db/src/add-members.ts`, the route `POST /api/working-groups/{id}/members` in `apps/api/src/routes/working-groups.ts`, the form `AddMembersForm` and `AddMembersResults` in `packages/ui`, and the button and modal in `apps/portal/src/pages/add-members.tsx`.

- **Who.** `workingGroup.addMembers`: the group's coordinators, the admins of its organization and platform admins; its volunteers get 403, anyone else 404. A group that is switched off may be added to.
- **One outcome per address,** each address in its own transaction, in the order of the list after `normalizeEmailList` (trimmed, lowercased, empty lines dropped, doubles once): `invalid` (not an address by `emailAddressSchema`; nothing written), `added` (no account, or an account that never logged in: a volunteer membership, the entry `membership.added`, `access-changed` and the queued mail `added-to-working-group`; a new account has no name), `already_member`, `approved` (the person has logged in and has a pending request for this group: it is approved as by a coordinator, and the API sends the approval mail directly) and `invited` (the person has logged in, without such a request).
- **Why someone who has logged in is invited instead.** Adding would show the adder their name and phone number, and pull a person of another organization into this one without asking. So they are not added: they get one mail (`invited-to-working-group`, with the entry `membership.invited`) that asks them to ask for the group themselves, in the app under Meer, Profiel, "Meld je aan bij nog een werkgroep". The answer holds the typed address and the outcome only, never a name or a phone number, and the same answer comes whether or not that person is in this organization.
- **Limits.** At most 200 addresses per request (`MAX_ADDRESSES_PER_REQUEST` in `packages/contracts`; more is 429 `too_many_addresses`, and the form refuses it first); at most 500 people added or invited per account in 24 hours, counted from the account's `membership.added` and `membership.invited` entries (more is 429 `too_many_additions`); both are checked before the first address, so a refused list changes nothing. No second invitation mail for the same person and working group within 24 hours (the answer is still `invited`). The same list twice, or the same address from two people at once, gives one membership, one account and one mail.
- **Removing someone who never logged in deletes the account too.** After the removal commits, `removeMembership` (`packages/db/src/members.ts`) calls `deleteAccount` with `onlyIfUnused` and the remover as `deletedBy`, in a second transaction, so an address with a typing mistake does not stay behind. If that fails, the removal stands: the result holds `cleanupError`, which `DELETE /api/memberships/{id}` logs with the error class and SQLSTATE only, and the answer is still 204.
- **Asking for another working group.** A member asks from Profiel: "Meld je aan bij nog een werkgroep" opens `/more/profile/join` (`apps/mobile/src/screens/more/join-another-screen.tsx`), part 1's picker over `otherWorkingGroups(me, directory)`; the hook `apps/mobile/src/lib/use-join-working-group.ts` is shared with the applicant's picker. While a request waits, Profiel shows "Je aanmelding bij {werkgroep} wacht op goedkeuring." with "Trek aanmelding in" instead of the button.

### Requests in the portal

The design is `docs/superpowers/specs/2026-11-22-portal-administration-design.md` ("Membership requests in the portal"). The list is `listReviewablePendingRequests` in `packages/db/src/membership-requests.ts`, the route `GET /api/membership-requests` in `apps/api/src/routes/membership-requests.ts`, the hook `useReviewableMembershipRequests` (`packages/api-client/src/membership.ts`), the table `MembershipRequestTable` in `packages/ui`, and the page `apps/portal/src/pages/membership-requests-page.tsx`.

- **The list.** `GET /api/membership-requests` gives the pending requests of every working group the actor reviews, with the applicants' contact details: all groups for a platform admin, every group of the organizations they administer (inactive ones too) and the active groups they coordinate; empty for anyone else. Sorted by organization, working group (both `COLLATE "nl-NL-x-icu"`) and oldest first. The page shows one table per working group, with the organization's name after the group's when the list spans more than one organization. `refetchMembershipRequests` always refetches it, so `membership-requests-changed` reaches it.
- **The modal.** `?request=<id>` opens that request in a `Modal` with `MembershipRequestDetail` (`confirmReject={false}`: "Wijs af" decides at once, the press is the decision). Opening it decides nothing; Escape, the cross or a click beside it closes it and removes `request` from the address (replacing the history entry). A decision shows a toast ("{naam} is toegelaten tot {werkgroep}." or "De aanmelding van {naam} is afgewezen.") and closes the modal; another error stays in the modal. A request the list lacks is asked for once with `GET /api/membership-requests/{id}`: a decided one gives the toast "Deze aanmelding is al behandeld.", one the actor may not see (404, 403) "Deze aanmelding bestaat niet meer.", and both close the modal; a pending one waits for a fresh list. A request decided by someone else while the modal shows it gives "Deze aanmelding is al behandeld." too. An answer that arrives after the user moved to another request or left the page changes nothing.
- **The navigation item** "Aanmeldingen" comes after Werkgroepen for everyone who manages something (`navigationFor`), with the sum of `pendingRequestCount` over `useManagedWorkingGroups` as a badge (`aria-label` "Aanmeldingen, {n} open").

### Species

The design is `docs/superpowers/specs/2026-11-22-portal-administration-design.md` ("Species").

- **One official list for all organizations.** `species` (`packages/db/src/schema/species.ts`, functions in `packages/db/src/species.ts`, routes in `apps/api/src/routes/species.ts`) is the one domain table that is not scoped by organization: every organization counts the same species. Do not copy that to tenant data. Every logged-in user may read the list (`GET /api/species`; it is not secret); only platform admins add or change a species (`platform.manageSpecies`, 403 for anyone else).
- **The first five species come from the migration `official_species`,** with fixed IDs (`officialSpeciesIds`), in every environment. That migration is never edited; a later change to the list is made in the portal, so it goes through the audit log, never by a migration. The seed adds no species.
- **A species is switched off, never deleted.** There is no delete function and no `DELETE` route: `PATCH /api/species/{speciesId}` with `active: false`. The counting screens (later) offer only active species; earlier counts keep a species that was switched off.
- **Names.** Stored as written in a sentence ("gewone pad"), with spaces trimmed and collapsed (`normalizeSpeciesName`); the apps capitalize the first letter (`capitalizeFirst`). Both names are unique regardless of capitals: a taken one is 409 `name_taken` with `issues[0].path` `dutchName` or `scientificName`. A name may not contain `@`, because the audit entry holds it. The list is sorted by Dutch name with `COLLATE "nl-NL-x-icu"`. The server makes a species' ID: adding one is administration, not a write from the field.
- **A change and its audit entry go in one transaction;** a save that changes nothing answers 200 and writes no entry.

### Sessions and login

- **The session cookie is `HttpOnly`, `Secure` and `SameSite=Lax`.**
- **A `GET` never changes state.** The server rejects state-changing requests whose `Origin` is not one of our own, and allows no cross-origin requests from other sites.
- **Rate-limit requesting and verifying login codes,** per email address and per IP address.
- **Login codes are valid for 15 to 30 minutes** and appear in the subject line of the email. Sessions are long-lived.
- Check what Better Auth already provides before building any of this yourself.
- **Better Auth is mounted as an allowlist,** not a catch-all: `AUTH_PATHS` in `apps/api/src/auth/auth-routes.ts` lists the three `POST` routes the apps use (`/api/auth/email-otp/send-verification-otp`, `/api/auth/sign-in/email-otp`, `/api/auth/sign-out`). Every other Better Auth endpoint (profile and password changes, session lists, `get-session`) answers 404. Add a route to the allowlist only deliberately, after checking what it lets a client do; these routes bypass our Zod contract and OpenAPI.
- **Who is logged in comes from `GET /api/me`,** never from Better Auth's `getSession` or `useSession` in the apps. The browser client in `@padvinder/api-client` (`requestLoginCode`, `logInWithCode`, `logOut`) uses only the three routes. `logOut()` resolves `{ ok: false }` when sign-out failed; then the app must not act as if the user is logged out. `DELETE /api/me` (`useDeleteAccount`) ends the session as well; the mobile gate sees the finished mutation (`deleteAccountMutationKey`) and shows the login screen with "Je account is verwijderd." until someone logs in again. Logging out never shows that notice.
- **Account and session IDs are made by the server** (Better Auth, with `uuidv7()` defaults in the database). They are not field writes, so the rule that the client generates the ID does not apply to them.
- Settings: a session lasts 180 days and is renewed once a day of use; a code is valid for 30 minutes. The limits per address and per IP address are in `apps/api/src/auth/login-rate-limit.ts`. `LOGIN_RATE_LIMITS=off` switches them off for local development and tests only; the API refuses it when `PUBLIC_ORIGIN` uses https. The cookie is `Secure` when `PUBLIC_ORIGIN` uses https (not on plain-http localhost). Sessions store no IP address or browser, and the login limits keep nothing longer than 24 hours. Only `requireActor` renews a session, because only it passes the refreshed cookie on; `loadActor` (the event stream's check, `/api/health`) reads without renewing. The sign-in answer leaves out the session token.
- **Both apps share one login gate:** `useAuthGate()` (`@padvinder/api-client`) with `AuthGateView` (`@padvinder/ui`). The Dutch login texts live in `packages/ui/src/lib/messages.ts`; the client reports a `LoginError` code (`@padvinder/contracts`). An applicant (`gateState` `choose` or `waiting`) sees what the app passes as `applicant` (the mobile app: the picker, the waiting screen and the profile, `apps/mobile/src/auth/applicant-shell.tsx`); the portal passes nothing, so applicants see its page.
- **Dutch texts for API errors** come from `apiErrorMessage(code)` in `packages/ui/src/lib/messages.ts`, with the code from `apiErrorCode(error)` (`@padvinder/api-client`); an unknown code or a network failure gives `connectionMessage`. Texts that more than one screen shows live in that file too.

### API and versioning

- **Zod schemas are the single source for the API contract.** They live in `packages/`. Fastify validates requests and responses with them, the OpenAPI description is generated from them, and the client is generated from the OpenAPI description. Infer TypeScript types from the schemas; do not write the same shape twice.
- **The API is backward compatible.** An open app keeps running old code. Only add fields; never rename or remove one while an old app version uses it.
- **Database migrations go in two steps:** add the new thing first, remove the old thing in a later release.
- **One error format.** Every error our own routes return has the shape `apiErrorSchema` (`packages/contracts/src/errors.ts`): Fastify's `statusCode`, `error` and `message` (English, for developers), plus `code`, a stable lowercase identifier from `apiErrorCodes`. Throw `apiError(status, code, message, issues?)` from `apps/api/src/errors.ts`; `issues` (`[{ path, message }]`) points at the field the error is about, as 409 `name_taken` does with `dutchName` or `scientificName` (the apps read it with `apiErrorIssues`), and list the error responses of each route with `...errorResponses(400, 401)` in `schema.response`. A validation failure is 400 `invalid_request` with `issues`. The apps choose their Dutch text from `code` and never show `message`.
- **Errors of the administration functions.** `packages/db/src/admin.ts` throws `AdminError` with a code; a route turns it into the API answer with `adminErrorToApiError(error, { email })` (or `mapAdminErrors`) in `apps/api/src/admin-errors.ts`, where `email` names the request field that holds the address, so `issues` points at it. Its 409 codes: `last_organization_admin`, `last_coordinator`, `no_coordinator`, `person_outside_organization` (with `issues` on the address field) and `name_taken` (for organizations and working groups as for species). Their Dutch texts are in `packages/ui/src/lib/messages.ts`. A name or city that is empty after `normalizeName` is `invalid_name` (with `field`, `name` or `city`), 400 `invalid_request` with `issues` on that field; the request schemas refuse it first, so only the administration tool meets it.
- **A typed email address** has one rule, `emailAddressSchema` (`isEmailAddress` for a yes or no) in `packages/contracts/src/email.ts`: trimmed and lowercased first, so sloppy typing reaches the same account, then a valid address of at most 254 characters, never the replaced address of a deleted account. The request schemas, the forms in `packages/ui` and `parseEmail` in `admin.ts` all use it; do not write a second check.
- **A long list is paged by a cursor on its sort key, never by an offset.** An offset skips or repeats rows when rows are written between two pages. The example is `listAuditLogEntries`: it sorts on (`occurred_at`, `id`) descending, answers `nextCursor`, `{occurredAt}_{id}` of the last entry (`auditLogCursorSchema` in `packages/contracts/src/audit-log.ts`), and the next page compares that pair as a row with the cursor's, served by the index on `audit_log_entries (occurred_at, id)`. The cursor's moment has six decimals, made by PostgreSQL (`to_char` in UTC) and read back as a `timestamptz`, never through a JavaScript `Date`, which keeps only milliseconds: entries microseconds apart would otherwise be skipped or read twice. Entries of one transaction share their moment and are told apart by `id`.
- **An email address goes in the body of a request, never in its path or its query,** because Fastify's request log and the host's HTTP logs hold the path and the query. The example is `POST /api/users/lookup` with `{ email }`, not `GET /users?email=…`; it matches one whole address after `emailAddressSchema`, never a part of one.
- **`DELETE /api/me` can be refused.** Besides 409 `last_platform_admin`, the only coordinator of an active working group or the only admin of an organization gets 409 with `blockers` (`accountDeletionBlockedSchema` in `packages/contracts/src/account-deletion.ts`): per group and organization its role, the names, and the organization's `contactEmail`. The code is `last_coordinator` when the first blocker is a group, else `last_organization_admin`. The app reads them with `accountDeletionBlockers(error)` (`@padvinder/api-client`) and shows one sentence per blocker (`accountDeletionBlockedMessage` in `packages/ui/src/lib/messages.ts`): whom to ask, the contact address or else the organization's admin or a platform admin.
- **`PATCH` takes a partial object.** A field that is present is changed, an absent field stays, `null` empties a field that may be empty. An unknown field or a body without any field is 400, so a typo never looks like a success (use `z.strictObject` and a refine that needs one field, as `updateMeRequestSchema`). Sending the same body twice gives the same result. This is the rule for every `PATCH`; no JSON Patch, no `PUT`.
- **Minimum version:** the API reports the minimum app version; an older app shows "Werk de app bij" and reloads.
- **App version** is CalVer `YYYY.N.P`, for example `2027.1.0`. The year is the migration season, not the release date: a release in December 2026 for the 2027 season is `2027.x`. The version lives in `apps/mobile/package.json`; `PADVINDER_APP_VERSION` overrides it. The build number is the CI run number, passed as `PADVINDER_BUILD_NUMBER` (default `dev`); it does not go into `PADVINDER_APP_VERSION`, which must be plain `YYYY.N.P` (the mobile build and dev server fail otherwise). The variable is not called `APP_VERSION` because Conductor sets that in its shells. Portal and API are identified by git commit.

### Frontend

- **Device features each live in their own module or hook** (position, wake lock, push, camera, vibration), so a later move to Capacitor touches few places. Do not add a general abstraction layer on top.
- **Shared code goes in `packages/`:** UI components, map, types and validation are written once and used by mobile, portal and API. Do not duplicate types between frontend and backend.
- **Never edit the generated OpenAPI description or the generated client by hand.** Change the Zod schema and regenerate.
- **UI components get Storybook stories with fixture data.** Stories are also the visual regression tests.
- **The input screen must work with one hand and wet fingers,** for users from young to old: large targets, high contrast, few steps.
- **Forwarding between app and portal.** The link in the coordinator's request mail is the app's address for the request, `{origin}/app/more/membership-requests/{id}`. At the top of each app's `main.tsx`, before anything renders (so before the login), a browser that opened the other app's page goes there with `window.location.replace`: the app sends a screen that is not a phone from `/app/more/membership-requests` and `/app/more/membership-requests/{id}` to the portal's `/membership-requests` and `/membership-requests?request={id}` (`portalAddressFor` in `apps/mobile/src/hooks/send-to-portal.ts`), and the portal sends a phone from those back to the app (`appAddressFor` in `apps/portal/src/send-to-app.ts`). An ID that is not a UUID is left out. A phone is `isPhoneScreen(window.screen)` (`packages/ui/src/lib/is-phone.ts`): the screen's shorter side under 600 CSS pixels, so a narrow window on a laptop is not one. In a build both apps share one origin; under the dev servers the other app is on its own port, from the Vite defines `__PORTAL_DEV_PORT__` (mobile) and `__APP_DEV_PORT__` (portal), `null` in a build. `e2e/portal-membership-requests.spec.ts` follows the link on a laptop and on a phone.
- **The portal.** `navigationFor(me)` (`apps/portal/src/layout/navigation.ts`) is the one place that decides which navigation items someone sees; later pages add their item there, and `/` goes to the first item. Hiding an item is convenience only; the API decides. A page someone may not see renders the not-found page, as if it did not exist (`RequirePlatformAdmin` and `RequireManagesSomething` in `apps/portal/src/layout/`; a group or organization the user's lists do not hold), and follows a change of rights without a reload. When the login screen replaces someone who was logged in (Log uit, or a session that ended), the address goes back to `/` (`onLoggedOut` of `AuthGate` in `apps/portal/src/auth/auth-gate.tsx`), so the next person starts at their own first page; someone who opens a page before logging in keeps it. Layout: `PortalLayout`. From `@padvinder/ui`: `Modal` is for a form or details, `ConfirmDialog` for a question with two buttons, and a result ("Gewone pad is gewijzigd.") shows with `showToast` (the layout renders the `Toaster`). Sonner keeps toasts between renders, so component tests call `dismissAllToasts()` after each test (`apps/portal/vitest.setup.ts`). The portal is for laptops and desktops; components of its pages use the `visualViewport` story parameter (see "Visual tests"). After Soorten come Logboek (`/audit-log`), for platform admins and organization admins (`readsAuditLog(me)` in `navigation.ts`, which the page uses too), then Hoofdbeheerders (`/platform-admins`) and Account verwijderen (`/delete-account`) for platform admins, before Systeemstatus.
- **Content is managed in the portal, not in code:** species, choice lists, count categories, drain types, help texts, FAQ, colors, settings and safety test versions. Do not hard-code what an admin should be able to change.

### Backend

- **Connect to PostgreSQL on port 5432, not through pgBouncer (5433).** pgBouncer breaks `LISTEN`/`NOTIFY`.
- **Fastify listens on `::`.** Alwaysdata services are reachable over IPv6 only.
- **Routes reach the user only through `request.actor`.** Add `preHandler: app.requireActor` to a route that needs a login: it sets `request.actor` (`Actor` in `apps/api/src/permissions/actor.ts`) or answers 401 `not_logged_in`. Never read the session cookie or call Better Auth from a route. Decide with `authorize` or `decide` (see "Roles and permissions").
- **API and worker communicate only through PostgreSQL.** The worker has no HTTP interface. Scheduling lives in the application (pg-boss), not in the hosting provider's cron. The API's only pg-boss use is queueing mails (see "Mail").
- **File access goes through the storage interface.** Never read or write uploads directly from feature code.
- **Remove expired push subscriptions** when the push service answers 410.

### Logging

The design is `docs/superpowers/specs/2026-11-26-logging-and-monitoring-design.md`. The code is `packages/logging`.

- **One logger.** The API and the worker log JSON lines through `createLogger({ service, level })` from `@padvinder/logging`; every line has `service`, `level` and `msg`. The level comes from `LOG_LEVEL` (default `info`). Both services also install the crash handlers (`installCrashHandlers`).
- **Errors go in as `{ err }`.** The `err` serializer (`serializeError`) keeps an allowlist of fields and never throws; a thrown value that is not an `Error` is logged as its type and, for an object, its keys only (never its values). Never put an error's own properties or a request object in a log line yourself.
- **Addresses are scrubbed as a safety net.** `scrub` runs on every finished JSON line through pino's `streamWrite` hook (`packages/logging/src/logger.ts`) and removes email addresses; `serializeError` also scrubs an error's `message`, `stack` and the text fields it keeps. This is a net, not permission: do not log an address (see the last rule below).
- **One line per request.** Fastify's "incoming request" line is off; its log controller (`OneLinePerRequest` in `apps/api/src/app.ts`) writes one line at `info`, "request completed", with `req` (method, the path without its query or fragment, host), `res.statusCode`, `responseTime` and `reqId`, never the client's address or headers.
- **Health checks stay quiet.** `/api/health` logs below `info` (its route has `logLevel: "warn"`, which `request.log` follows), so only a warning shows.
- **Tests read the log** with `createTestLogger` from `@padvinder/logging/testing` (`entries()` for parsed lines, `text()` for the raw output).
- **`pnpm dev` pretty-prints** the API and worker logs through `pino-pretty`; staging and production write JSON.

What to log at which level:

- **`error`:** a person must look at it. It becomes a Sentry issue. Examples: an unexpected error behind a 500, a mail dropped after its last try, a pool error, a job that failed.
- **`warn`:** unusual but handled, often with a retry. Examples: a mail that will be tried again, the notification listener reconnecting, the health check not reaching the database.
- **`info`:** the life of the process and one line per request. Start, stop, request lines.
- **`debug`:** detail for development.
- **Never in a log line or an error message:** a name, an email address, a phone number, an IP address, a cookie or header, a login code, a request body, or a coordinate. IDs are fine. When a value would help, log its kind or its length.

### Monitoring

The design is `docs/superpowers/specs/2026-11-26-logging-and-monitoring-design.md`; the code is `packages/monitoring`. Sentry has two projects: `padvinder-server` (API and worker, and the uptime monitor; `SENTRY_DSN`) and `padvinder-browser` (app and portal, and the problem reports; `SENTRY_BROWSER_DSN`, used by the API only; the worker checks it at start-up through `readMonitoringSettings` but does not use it). The API and the worker share a project; the tag `service` tells them apart. Sentry is off on the server without `SENTRY_DSN`, and the tunnel and problem reports drop what they get without `SENTRY_BROWSER_DSN` (locally, in tests, in CI and in the container smoke test). The organization checklist, the secrets and the rollout are in `infra/alwaysdata/README.md`, "Sentry".

- **Sentry starts first.** `apps/api/src/main.ts` and `apps/worker/src/main.ts` import only `@padvinder/monitoring`, read the settings, call `startServerMonitoring`, and then load the program with `await import("./run")`. Sentry's `pg` instrumentation hooks the module when it is loaded, and the bundle hoists every static import of an external package to the top of the file, so any other static import in `main.ts` would load `pg` before Sentry. Do not add one: `scripts/server-bundles.test.ts` builds both apps and fails when `dist/main.js`, through the chunks it imports statically, loads `pg`, `pg-boss`, `drizzle-orm`, `fastify`, `better-auth` or `nodemailer`. An invalid `SENTRY_DSN` (not a DSN by `parseDsn`, which `infra/alwaysdata/src/config.ts` repeats as `isHttpsDsn`) or `PADVINDER_ENVIRONMENT` (`readMonitoringSettings`) stops the service with only that message (never the value), before the rest of the environment is checked.
- **`error` lines are the issues.** Sentry's pino integration turns each `error` line into one event; the Fastify integration's own capture is off (`shouldHandleError: () => false`), so an error that is thrown and logged is one event, not two. Crashes are logged at `error` by the crash handlers, flushed with `flushMonitoring`, and then the process exits.
- **The data-collection rule.** `dataCollection` lists every category and turns it off: user info, cookies, headers, bodies, query strings, query data, queues, stack frame variables and the AI inputs. Since Sentry 11 an unset category is on, so never remove one. The only user field is `{ id }`. `beforeSend`, `beforeSendTransaction` and `beforeBreadcrumb` run every string through `scrub`, with `%40` read as `@` (`scrubEvent`, `scrubBreadcrumb`), and cut the query and fragment from every URL value (`URL_KEYS`: `url.path`, `url.full`, `http.target`, `http.url`, `url`, wherever they appear), because Sentry's Fastify instrumentation puts the raw `request.url` in `url.path` whatever `urlQueryParams` says; `scrubEvent` also removes request headers, cookies, body and query string, any user field but `id`, and the span attributes in `DROPPED_SPAN_ATTRIBUTES` (`user_agent.original`, which the SDK sets whatever `dataCollection` says, and the query and fragment attributes). It passes `sdkProcessingMetadata` on as it is: the SDK never sends it. `beforeBreadcrumb` is load-bearing: the SDK skips `beforeSend` for its own internal-exception events, which still carry the scope's breadcrumbs.
- **`traceLifecycle: "static"`.** The default since 11 streams spans one by one and skips `beforeSendTransaction`, so their text would go out unscrubbed. Static sends one transaction with its spans, which `beforeSendTransaction` scrubs. Do not change it.
- **Tracing.** Every request and job is sampled (`tracesSampler`), except `/api/health`, `/api/events`, everything outside `/api/` (the apps' static files) and the worker's `heartbeat` job. Add spans with `withSpan(name, op, attributes, fn)` (the mail send does); `runJobInSpan({ name, id }, fn)` wraps a pg-boss job in a trace of its own with the tags `job.name` and `job.id`. Work that outlives its request, such as a mail sent with `sendInBackground`, runs in `runInNewTrace`, its own trace in its own isolation scope, so its span does not end after the request's transaction was sent. Attributes are IDs and kinds, never a name, address or text.
- **The user.** `setMonitoringUser(id)` sets `{ id }` on the current isolation scope. The API sets it only in `requireActor` (through `identify` in `apps/api/src/permissions/actor.ts`). `loadActor` (the event stream and `/api/health`) never sets it: the event stream reloads its actor outside the request, and Sentry clones the ambient isolation scope into later requests, so a user set there would end up on someone else's events. Never call `setMonitoringUser` from code that can run outside a request.
- **Tests.** `createTestTransport` and `startFakeSentry` from `@padvinder/monitoring/testing` capture what would be sent (a transport in memory, or a local HTTP server standing in for Sentry); check the raw events for personal data, as the API tests do for `POST /api/system/test-error`. Pass a transport to `startServerMonitoring` instead of a DSN in a test.
- **`POST /api/system/test-error`** (`system.triggerTestError`, platform admins only) runs a query and throws, so the answer is 500 `internal_error` and Sentry gets one issue with a trace holding the query. It is how "Verification" in `infra/alwaysdata/README.md` checks the setup on staging.
- **Stack frames are relative to the release.** `startServerMonitoring` rewrites each frame's `filename` and `abs_path` to `app:///api/dist/...` (relative to `process.cwd()`, the release directory; the option `root` is for tests), so the home directory of the server account never reaches Sentry. Sentry matches a source map by the debug ID, which the SDK takes from the file before the rewrite and then writes to `debug_meta` with the rewritten path as `code_file`, so resolution does not depend on the path. A failed start of the API closes monitoring in a `finally` and again in `run.ts`, so its "API failed to start" event is sent even when the cleanup throws.
- **Sentry never blocks the app.** Events are sent in the background; on shutdown the API and the worker flush for about 2 seconds (`flushMonitoring`, `closeMonitoring`), and neither can reject.
- **The browser.** `startBrowserMonitoring` (`packages/ui/src/monitoring/browser-monitoring.ts`) runs at the top of each app's `main.tsx`, before the first render, in a production build only: it is off under the Vite dev servers, so a developer's crash never reaches Sentry. The DSN in the bundle is the placeholder `https://public@padvinder.invalid/1` (`PLACEHOLDER_DSN`); the SDK sends everything to `tunnel: "/api/sentry-tunnel"`, so the real DSN never reaches a browser and an ad blocker that knows Sentry's host sees nothing. The same data-collection rule as the server applies (every category off, `traceLifecycle: "static"`, `beforeSend`, `beforeSendTransaction` and `beforeBreadcrumb` scrub through `scrubBrowserEvent` and `scrubBrowserBreadcrumb`, which also strip attribute values from selectors). At most 10 error events leave a page load (`MAX_ERRORS_PER_PAGE_LOAD`), so a phone in an error loop costs 10 events, not hundreds. The console integration is off, the INP web vital is off (it sends the tapped element's selector), and `ui.click` and `ui.input` breadcrumbs keep only the path to the tapped element as tag names and the names of a few attributes (`elementPath`): never its text, id, classes or attribute values. Network errors without a connection ("Failed to fetch" and its Safari and Firefox forms) are ignored as the whole message; the API reports its own 5xx. A failed load of a code chunk after a deploy reloads the page once (`reloadOnPreloadError`). Tags `service` (`app` or `portal`) and `app_version`; the release is the build's commit (`__GIT_COMMIT__`, from `GIT_COMMIT`, which `scripts/build-release.sh` sets; `dev` otherwise). The only user field is `{ id }`: each app's `AuthGate` sets it through `useBrowserMonitoringUser` (`setBrowserMonitoringUser`), and clears it on logging out.
- **The tunnel.** `POST /api/sentry-tunnel` (`apps/api/src/routes/sentry-tunnel.ts`) needs no login. It rescrubs every envelope on the server as defence in depth (`prepareBrowserEnvelope` in `packages/monitoring/src/envelope.ts`, so a bug in the browser's scrubbing is not the only line of defence): it keeps only the item types `event`, `transaction`, `session`, `sessions` and `client_report` and drops replays, attachments and the rest; runs every string through `scrub`; removes the session attributes `user_agent` and `ip_address` and `sdkProcessingMetadata` everywhere; sets the browser project's DSN and environment; keeps the browser's release (on events, transactions, sessions and the header's trace) when it is a full 40-character commit, because an installed app runs its old build until it is updated and its errors belong to that release, and sets the server's release otherwise (`dev`, anything else); and forwards the result to `SENTRY_BROWSER_DSN`'s ingest address with none of the phone's headers, so Sentry sees Alwaysdata's address, not the phone's. Sentry's answer comes back for 2xx and 429 (with its rate limit headers, which the SDK obeys), 502 `sentry_unavailable` for anything else; without `SENTRY_BROWSER_DSN` the tunnel answers 204 and drops the envelope. The body limit is 200 KiB (413) and the limit is 120 envelopes a minute per client address (429 `too_many_requests`, `SENTRY_TUNNEL_LIMIT`), in the process's memory. The client address is `clientAddress`: a single-valued `X-Forwarded-For`, else one bucket shared by everyone (see the open row in `infra/alwaysdata/README.md`, "Verification"). The route is hidden from the OpenAPI description (`hide: true`), so it is not in the generated client; the browser SDK is its only caller.
- **Source maps of the browsers.** The release build also injects debug IDs into the mobile and portal bundles and moves their maps to `release/sourcemaps/mobile` and `release/sourcemaps/portal` (see "Release"); the browsers never get a map, and Sentry finds one by the debug ID.

### Problem reports

The design is the same spec ("Problem reports"). "Meld een probleem" sends what a logged-in user writes to the makers of PadVinder as Sentry user feedback in the browser project. The contract is `problemReportRequestSchema` (`packages/contracts/src/problem-reports.ts`, strict): `message` (1 to 2000 characters), `includeContact`, `page`, `appVersion`, `app` and optionally `eventId`, the ID of the crash event the report is about. The route is `POST /api/problem-reports` (`apps/api/src/routes/problem-reports.ts`), the hook `useReportProblem` (`packages/api-client/src/problem-reports.ts`).

- **Built on the server and posted directly.** `buildFeedbackEnvelope` (`packages/monitoring/src/feedback.ts`) makes the envelope and `forwardEnvelope` posts it, instead of `captureFeedback` in the background, so the API knows Sentry's answer: 204 when Sentry took it, 502 `report_not_sent` when it did not (the form keeps the text and says so), 429 `too_many_reports` after 10 reports per account per hour. Without `SENTRY_BROWSER_DSN` a report is only logged, with its length and never its text, and answers 204.
- **Contact only by opt-in, from the profile.** The message and the page go through `scrub`. The name and address are never in the request body: with `includeContact` the server takes them from the actor's profile (a name only when the profile has one), and they are the one thing not scrubbed. Without it the report holds only the account ID, as every other event does. On production an alert rule mails the maintainer for every new problem report (see "Sentry" in `infra/alwaysdata/README.md`).
- **The screens.** `ProblemReportForm` and `CrashFlow` are in `packages/ui/src/components/problem-report/`, with stories. In the app it is "Meld een probleem" in the Meer menu (`/more/report-problem`); in the portal a button in the header bar, next to the user's name, opens the form in a modal. A crash shows `CrashScreen`: "Vertel wat er gebeurde" opens the form in place, because the router may be what crashed, and the report is linked to the crash event when that event was sent (`captureCrash`, `sentErrorEventId`). Before the login the crash screen has no report button, since the endpoint needs an account. The app also has a not-found screen.

### Mail

The design is `docs/superpowers/specs/2026-11-22-portal-administration-design.md` ("Mails", "The mail queue").

- **All mail code is in `packages/mail`:** the texts, the SMTP mailer (`createSmtpMailer`, with `smtpSettingsShape` for the env of the API and the worker; it puts `MAIL_SUBJECT_PREFIX` before every subject, so a text never does) and the queue. Every mail starts with `greeting(name)`: "Hallo {naam}," or "Hallo," without a usable name, on one line. The login code mail passes `withoutDigits`, so it holds no digit besides the code; the API looks the name up first and sends without one when that fails. Names in a mail go through `singleLine`, and into HTML through `escapeHtml`.
- **Two ways out.** The login code, the request mail and the decision mails leave the API directly, with `sendInBackground` after the commit (see "Reference examples for accounts and access"). The mails about appointing and adding people go through the queue: `added-to-working-group`, `invited-to-working-group`, `organization-admin` and `first-coordinator`. Only the portal's endpoints queue mails, through the option `queueMail` of the functions in `packages/db` (`AppointmentOptions`); the administration tool, the seed and the test helpers pass none and send nothing. Someone who appoints themself (an admin who stays the first coordinator of their new group) gets no mail.
- **A queued mail is a `MailJob`** (`mailJobSchema` in `packages/db/src/mail-jobs.ts`): the kind and IDs, nothing else, strict. Queue it with `queueMail(tx, job)` in the transaction that makes the change, like `notify`, so it exists exactly when the change was committed. At sending time `loadMailJobData` loads the address and the names; it returns null, and the mail is dropped, when the receiver or what the mail is about is gone (a removed membership, a deleted account). `buildMailForJob` (`packages/mail/src/job-mail.ts`) builds the text, with links from `PUBLIC_ORIGIN`: the app is `{origin}/app/`, the portal `{origin}/`.
- **The worker sends them:** `registerMailJob` in `apps/worker/src/jobs/mail.ts`, on the pg-boss queue `mail` (`MAIL_QUEUE`, `MAIL_QUEUE_OPTIONS` in `packages/mail/src/queue.ts`). One mail at a time, at least 2 seconds apart (`MAIL_PAUSE_MS`); a failed send is tried 5 more times with pauses that grow from about a minute to at most an hour, and a finished job is gone within a day. pg-boss stores what the handler throws, so the worker throws only a `MailJobError` with the kind and `describeMailError`, never an address; a dropped mail is logged with its kind only.
- **The API has its own pg-boss instance, only to queue:** `startMailQueue` in `apps/api/src/mail/mail-queue.ts`. It runs no workers, no schedules and no maintenance (`supervise`, `schedule` and `registerInstance` off), has its own pool of 2 connections (connect timeout 2 s, query timeout 31 s), and starts on the first queued mail, not at boot; a failed start fails that change and the next mail tries again. It migrates (pg-boss's default), so the API can make the pg-boss schema on a fresh database before the worker ever ran; that also runs pg-boss's background-migration poller and queue-cache refresh in the API process. API tests get a memory queue instead: `createTestApp()` passes `createMemoryMailQueue()` and exposes it as `ctx.mailQueue` (`ctx.mailQueue.jobs`).
- **To add a kind of mail:** a member of `mailJobSchema` with IDs only; its variant of `MailJobData` and a case in `loadMailJobData` that answers null when something is gone; its text in `packages/mail`, starting with `greeting`; a case in `buildMailForJob`. The switches are exhaustive, so a missing case does not compile. Then queue it with `queueMail` where the change is made.

## Platform constraints (PWA)

| --------------------- | ------------------------------------- | ----------------------------------------------------------------------------------------------- |

### Reference example: the health endpoint

Copy this slice when you add a feature; it touches every layer. `packages/contracts/src/health.ts` (Zod schema) -> `packages/db` (diagnostics, worker heartbeats) -> `apps/api/src/routes/health.ts` -> `openapi.json` -> `@padvinder/api-client` (`healthQueryOptions()`, `useHealthLiveUpdates()`) -> `packages/ui` `HealthStatus` with stories -> mobile "Meer" tab and portal `/system` -> `e2e/mobile-system-status.spec.ts`.

- Use `healthQueryOptions()`, not `getHealthOptions()`: a 503 with a degraded body is data, not an error.
- Realtime pattern: the worker sends `NOTIFY`, the API notification hub `LISTEN`s (with a `select 1` liveness check, and reconnects with capped backoff), `/api/events` streams SSE, and the client patches the TanStack Query cache and refetches when the stream (re)opens.
  - All live events go over one channel, `liveEventsChannel` (`live_events`, in `packages/db/src/notifications.ts`), whose payload is the `liveEventSchema` union in `packages/contracts/src/events.ts`. The `type` is the SSE event name. Each type has one audience, which decides which connections receive it (`shouldDeliver` in `apps/api/src/realtime/audience.ts`): `user` (carries `userId`; that user), `working-group-coordinators` (carries `workingGroupId` and `organizationId`; coordinators of that group and admins of its organization), `working-group-members` (same IDs; every member of the group and admins of its organization), `organization` (carries `organizationId`; everyone with a membership or admin row there) and `platform-admins`. Platform admins receive every event except those for `user`: an event addressed to one person reaches only that person, so later personal messages stay private. An event that lacks an ID its audience needs reaches platform admins only (nobody, for `user`). To add an event:
    1. Add a union member in `packages/contracts/src/events.ts`, with the IDs its audience needs, and declare its audience in `liveEventAudiences` in the same file. The map is complete: a type without an audience does not compile.
    2. Call `notify(tx, liveEventsChannel, {...})` in the transaction that commits the change (it accepts no plain `db`, so nothing is sent on rollback). The payload must stay under 8000 bytes: send IDs, not records.
    3. Add a handler under `events` in `subscribeToServerEvents`.
  - A separate channel with `defineChannel(name, zodSchema)` is only for a different consumer; add it to `channels` in `apps/api/src/start-api.ts` too, otherwise `hub.subscribe` throws.
- `/api/events` needs a login (`requireActor`; 401 without one) and delivers each event only to the connections of its audience. An open stream loads its actor again at least every 5 minutes (`SESSION_RECHECK_MS` in `apps/api/src/routes/events.ts`), so changed rights take effect; a database failure during that check keeps the old actor and tries again at the next interval. When the session is gone, the stream ends and the browser's reconnect gets a 401. `subscribeToServerEvents` then calls `onClosed` and opens the stream again after a growing pause (also after a 502 during a deploy); every subscriber invalidates the me query in `onClosed` (as `useHealthLiveUpdates` does), so a logged-out app shows the login screen. `useAccessLiveUpdates` (`packages/api-client/src/access-live-updates.ts`, mounted by the mobile gate while someone is logged in, and by the portal layout `apps/portal/src/layout/portal-layout.tsx`) refetches me on `access-changed` and the request lists on `membership-requests-changed`, and both on every (re)open.
- `/api/health` is public, but its `database` details (versions, latest migration) are for platform admins only (`decide(actor, { action: "system.viewDatabaseDetails" })`); everyone else gets `detailsHidden: true`. The `worker-heartbeat` event has the audience `platform-admins`. The mobile "Meer" tab and the portal `/system` show the system status only to platform admins, and `e2e/mobile-system-status.spec.ts` makes its platform admin with `runAdmin`.
- The idempotent write is the membership request (see "Reference examples for accounts and access"). `PATCH /api/me` is idempotent by the `PATCH` rule instead.

### Reference examples for accounts and access

Copy these when you write the same kind of thing:

- **An idempotent write from the app:** `POST /api/membership-requests` (`apps/api/src/routes/membership-requests.ts`, `createMembershipRequest` in `packages/db/src/membership-requests.ts`). The app makes a UUIDv7 when the user taps and sends it on every resend; the server answers 201 for `created` and 200 for `existing` (nothing changes, no second mail), 409 when the ID belongs to someone else. A per-user advisory lock and one retry after a unique violation cover two requests at the same moment.
- **A change with its audit entry and live events in one transaction:** `decideMembershipRequest` in `packages/db/src/membership-requests.ts`.
- **A response that leaves out fields by permission:** `listMembers` in `packages/db/src/members.ts` (no `email` and `phone` keys at all without `contact`; `apps/api/src/routes/members.test.ts` checks the raw JSON).
- **A rule on the last one, under a lock:** `setCoordinator` in `packages/db/src/admin.ts` (lock the working group, read again, count, change, audit entry and `access-changed`), with its tests of two changes at the same moment in `admin.test.ts`.
- **Mails after the commit:** `sendInBackground` in `apps/api/src/mail/send-in-background.ts`, called after the transaction, never awaited by the request; a failure is only logged.
- **A mail through the queue:** `addMemberByEmail` in `packages/db/src/add-members.ts` queues `added-to-working-group` with `queueMail(tx, job)` in its transaction; the worker's `registerMailJob` sends it (see "Mail").
- **Adding by address, one transaction per address, under the locks of `deleteAccount`:** `addMemberByEmail`, with its tests of the same list from two people at once in `add-members.test.ts`.
- **Which screen the user sees:** `gateState` in `packages/api-client/src/gate.ts` (login, name, choose, waiting, app), shared by mobile and portal.
- **A client-generated ID:** `newId` in `apps/mobile/src/lib/new-id.ts`, called when the user acts, never while rendering.

### CI

GitHub Actions, `.github/workflows/ci.yml`, on every pull request and on `workflow_dispatch`. The job names are the required status checks (see `docs/repository-settings.md` for the repository settings, which the maintainer applies by hand):

`check` and `scan` run on every pull request. `visual`, `e2e`, `release / build` and `deploy-test` run only when the pull request changes something they test: a job `changes` feeds the changed paths to `scripts/ci-changes.ts`, whose rules are in `scripts/lib/ci-jobs.ts`. Documentation and unit tests alone skip all four; `visual` runs only for `packages/ui`, the workspace packages it depends on, and its script; `deploy-test` only for the deploy path (`infra/`, the deploy workflows and action, the release build, the migrate and main entry points), and then `release` runs too; dependencies, the tool chain and the CI files run everything; a path no rule knows runs `e2e` and `release`. A skipped job reports as passed, so it still satisfies the required check. If `changes` fails, or on `workflow_dispatch`, everything runs. When you add a file that one of these jobs depends on outside the paths it already covers, add it to the rules and their test.

- `check`: `pnpm check` against a PostGIS service container (includes the generated-files check).
- `visual`: the Storybook visual tests in the Playwright image. Failures upload `visual-diffs`.
- `e2e`: Playwright end-to-end tests against `pnpm dev`, in the Playwright image, with PostGIS and Mailpit as service containers and made-up login variables (not secrets).
- `scan`: gitleaks over the whole history, and actionlint (`pnpm scan:secrets`, `pnpm lint:workflows`).
- `release / build` (the reusable `build-release.yml`): builds the release, builds the container image from the tarball, smoke-tests it, and uploads the tarball as artifact `release-<full commit sha>`. The deploy workflow calls it too and deploys that tarball.
- `deploy-test`: runs `pnpm test:fake-host` with that tarball (the deploy scripts over SSH against a fake host container), and runs the credentials action with a throwaway key.

The CI workflow uses no secrets. The Deploy workflow's step "Upload source maps" uses the secrets `SENTRY_AUTH_TOKEN` and `SENTRY_ORG` (a secret so the public logs never show the organization's slug); Provision writes `SENTRY_DSN` and `SENTRY_BROWSER_DSN` to the env file. Only the deploy workflows (`deploy.yml`, `provision.yml`, `staging-services.yml`) do, through the GitHub environments `staging` and `production`. All workflows run with read-only permissions, except `rotation-reminder.yml`, which opens a yearly issue to rotate the secrets and is the only workflow with write permission (`issues: write`, nothing else). All workflows pin every action to a full commit SHA. Tools run as pinned Docker images from scripts in `scripts/`, so the same command works locally. Dependabot (`.github/dependabot.yml`) opens weekly update pull requests for npm, GitHub Actions and Docker files. It does not update the `container:` and `services:` images inside workflows: update those by hand (the Playwright tag together with the package, see "Visual tests").

### Workflow and deployment

- **Every change goes through a pull request and CI,** also with one developer. Short-lived branches from `main`.
- **Branch protection** on `main` requires the CI checks; see `docs/repository-settings.md`.
- **Do not install dependencies on the server.** The artifact contains everything.

#### Deployment

Merging to `main` builds one release and deploys it to staging; production follows after the maintainer approves it in the run. The production job deploys that run's commit only while it is still the current release of `main`: newer commits that change only ignored paths do not count. If a newer commit changes the release, the job deploys nothing and fails, and that commit's own run deploys it (`scripts/deploy-current.ts`, which reads `paths-ignore` from `deploy.yml`). A merge that changes only documentation, unit tests, stories, screenshots or end-to-end tests deploys nothing (`paths-ignore` in `deploy.yml`). Only `main` deploys or provisions: both environments are on one Alwaysdata account, where every SSH user and API token reaches everything, so the GitHub environments `staging` and `production` allow the branch `main` only. A branch reaches staging only by merging it, or by the maintainer running the CLI locally. Migrations run on the server before the services restart; a failed health check switches back to the previous release. Provisioning (`pnpm infra:provision`, or the Provision workflow run by hand from `main`) makes the Alwaysdata sites, services and databases, and writes the env file. It creates no SSH user: provisioning and deploys log in as the account's main SSH user, named like the account. Staging shares 1 GB of RAM with production and may be switched off (the Staging services workflow).

Everything else is in `infra/alwaysdata/README.md`: what runs where, the one-time GitHub and Alwaysdata setup, the first-run order, operating notes (rollback, rotating secrets, logs), DNS, rebuilding on another host, and the checklist of what is not yet verified. Update it in the same pull request when you change a deploy script, a workflow or an environment name.

### Tests

Every change has tests, with no exception for small changes. What that means depends on the change:

| Change                                    | Test it needs                                                                                                                                                                                    |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Logic, validation, calculations           | A Vitest unit test                                                                                                                                                                               |
| API endpoint                              | A test against a real PostgreSQL with PostGIS, not a mock: the success case, a rejected invalid request, and the permission cases below                                                          |
| Anything behind a permission              | A test for each role that may, one for a role that may not, and one showing that a user from another organization is denied. Where working groups matter, also a user from another working group |
| Endpoint that takes writes from the field | A test that sends the same ID twice and finds one record                                                                                                                                         |
| Export or download                        | A test that the output contains no volunteer names                                                                                                                                               |
| UI component                              | A Storybook story with fixture data, which is its visual test; a Vitest component test for behavior                                                                                              |
| Flow across several screens               | A Playwright test                                                                                                                                                                                |
| Bug fix                                   | A test that fails without the fix                                                                                                                                                                |
| Database migration                        | Run it against a database that already holds data in the old shape                                                                                                                               |
