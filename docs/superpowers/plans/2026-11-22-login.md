# Login Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build pull request 1 of "Accounts and access": a person logs in with a one-time code by email in the mobile app and the portal, gives their name, and logs out; `/api/me` and the event stream need a login.

**Architecture:** Better Auth runs as a library inside the Fastify API, mounted on `/api/auth/*`, with its tables defined in `packages/db` and migrated by Drizzle Kit. The apps use Better Auth's browser client for three calls only (send code, sign in, sign out); everything else goes through our Zod contract, starting with `GET` and `PATCH /api/me`. Mail leaves over SMTP through a small mailer interface: Mailpit locally, an in-memory mailer in Vitest.

**Tech Stack:** Better Auth 1.7.27 (email OTP plugin, Drizzle adapter), nodemailer, Mailpit, and the existing stack (Fastify 5, Zod 4, Drizzle 1.0 RC, React 19, TanStack Query 5, Vitest 5, Playwright).

**Spec:** `docs/superpowers/specs/2026-11-21-accounts-and-access-design.md` (read it and `AGENTS.md` before starting any task). This plan covers item 1 under "Order of work". Plans 2 and 3 are `2026-11-22-access-model.md` and `2026-11-22-joining.md`.

## Global Constraints

- AGENTS.md applies in full: English code, Dutch UI copy with "je", English kebab-case URL paths, glossary terms, naming per location, generated files never edited by hand.
- Run `pnpm check` before every commit. After any change to a route or contract run `pnpm api:generate`; after any schema change run `pnpm db:generate`. Commit the generated files.
- Pin `better-auth@1.7.27` exactly (no `^`), in every package that imports it. If pnpm's minimum release age blocks it, add an exact-version entry to `minimumReleaseAgeExclude` in `pnpm-workspace.yaml`.
- Better Auth 1.7 is newer than the plan author's knowledge. Where this plan names a Better Auth option, endpoint or error code, it states the intent as documented on 21 November 2026; check the installed version's documentation and keep **our** names, signatures, tables and tests exactly as given here. If Better Auth cannot do something a test here demands, stop and report it; do not work around it silently.
- All IDs are `uuid` columns. Every moment is `timestamptz` in the database and ISO 8601 with offset over the API (`z.iso.datetime({ offset: true })`).
- Tables and columns are snake_case, tables plural: `users`, `sessions`, `accounts`, `verifications`, `rate_limits`, `login_code_requests`.
- There is no fixed login code and no switch that skips the code check, in any environment.
- The login code is never written to a log. Email addresses and names are not logged at `info` level or above.
- Fixtures, seed data and test addresses are made up and end in `@example.test`.
- Dutch copy in this plan is exact. Where a small text is missing, write it in the same style (AGENTS.md, "Dutch copy").
- A runtime dependency used by a bundled app must be a direct dependency of that app, with the same version as in the packages that use it (AGENTS.md, "Repository layout").
- Commit after every task with a message in English, ending with the co-author line your session's instructions give.

## Review Focus

1. **The mail server is down or slow.** Asking for a code must still answer quickly and must not crash the API; the failure is logged; the user can ask again. Pinned in Task 5 ("a failing mailer does not fail the request").
2. **The code arrives in odd shapes.** Pasted as `123 456` or `123-456`, autofilled, or starting with zeros (`012345` is a text, not a number). Pinned in Task 9 (`normalizeCode`, which keeps a leading zero) and Task 5 ("a code is always six digits of text").
3. **The address is typed sloppily.** `" Noor@Example.TEST "` must reach the same account as `noor@example.test`. Pinned in Task 5.
4. **The session ends while the app is open** (expired, logged out on another device). The next API call gets 401 and the app goes back to the login screen instead of showing errors. Pinned in Task 8 (`meQueryOptions`) and Task 10 (`AuthGate`).
5. **A code is used twice, or an old tab submits an old code.** The second use gets the "wrong code" message, never a crash or a second session for a stranger. Pinned in Task 5 ("a code works once").

### Task 2: One error format

**Files:**

- Create: `packages/contracts/src/errors.ts`, `apps/api/src/errors.ts`

**Interfaces:**

- Produces (from `@padvinder/contracts`):
  - `apiErrorSchema` (OpenAPI component `ApiError`): `{ statusCode: number; error: string; message: string; code: string; issues?: { path: string; message: string }[] }`, `type ApiErrorBody`.
  - `apiErrorCodes`, a `const` object of the known codes. In this plan: `invalid_request`, `not_logged_in`, `not_allowed`, `not_found`, `origin_not_allowed`, `too_many_requests`, `internal_error`. `type ApiErrorCode`.

  - `addErrorHandling(app: FastifyInstance): void`: sets the error handler and the not-found handler for paths under `/api`. An `ApiError` becomes its body; a validation error becomes 400 `invalid_request` with `issues`; any other error is logged and becomes 500 `internal_error` with the message `Internal server error` (never the original message).
  - `errorResponses(...statusCodes: number[]): Record<number, typeof apiErrorSchema>`, for a route's `schema.response`.
- The Origin hook answers 403 with `code: "origin_not_allowed"`. `message` is English and for developers; the apps never show it.
