# Joining a Working Group Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build pull request 3 of "Accounts and access": a new volunteer chooses a working group and waits; a coordinator approves or rejects in the app; members see each other; a user edits their profile and deletes their account; mails and live events keep everyone informed.

**Architecture:** The membership request is the first idempotent write: the app makes a UUIDv7 once and the server returns the stored record on a resend. Every change (request, decision, removal, deletion) is one function in `packages/db` that does the work, writes the audit entry and sends the live events in a single transaction; routes only authorize, call it, map the outcome to a status, and send mails after the commit. The mobile app decides its screen from `/api/me` through one pure function.

**Tech Stack:** The existing stack, plus the `uuid` package (version 7 IDs in the app) and shadcn's alert dialog.

**Spec:** `docs/superpowers/specs/2026-11-21-accounts-and-access-design.md` (read it and `AGENTS.md` before starting any task). This plan covers item 3 under "Order of work". It builds on `2026-11-22-login.md` and `2026-11-22-access-model.md` (both merged).

## Global Constraints

- AGENTS.md applies in full: English code, Dutch UI copy with "je", English kebab-case URL paths, glossary terms, naming per location, generated files never edited by hand.
- Run `pnpm check` before every commit. After any change to a route or contract run `pnpm api:generate`; after any schema change run `pnpm db:generate`. Commit the generated files.
- Routes reach the user only through `request.actor` and decide only through `authorize` or `decide` (`apps/api/src/permissions/rules.ts`). Every endpoint behind a permission has one `expectStatuses` test with the standard cast.
- Answers: 401 without a login; 404 for a record the actor may not see at all; 403 for one they may see but not change; 409 for a conflict; 429 over a limit. Error bodies follow `apiErrorSchema`; the apps choose the Dutch text from `code` and never show `message`.
- A response never contains a field the actor may not see. Leave the key out; do not send `null` in its place. Tests check the raw JSON.
- A change, its audit entry (`recordAudit`) and its live events (`notify`) go in one transaction. Mails go out after the commit, are never awaited by the request, and a failure is only logged.
- The audit log and the server log never hold a name, an email address or a phone number.
- All IDs are `uuid`; every moment is `timestamptz` and ISO 8601 with offset over the API. The time of the action (`requestedAt`, from the app) and the time of arrival (`receivedAt`, from the server) are both stored.
- The API stays backward compatible: only add fields to existing responses.
- Sort Dutch names with `COLLATE "nl-NL-x-icu"`.
- Fixtures, seed data and test addresses are made up and end in `@example.test`.
- Dutch copy in this plan is exact. Where a small text is missing, write it in the same style.
- Commit after every task with a message in English, ending with the co-author line your session's instructions give.

## Review Focus

1. **The same request arrives twice at the same moment** (a double tap, or a resend that crosses the first answer). One row, one mail, and both callers get the record. Pinned in Task 3.
2. **Two coordinators decide at the same moment, one approving and one rejecting.** Exactly one decision is stored, the other caller gets 409, and there is at most one membership. Pinned in Task 4.
3. **The request changed under the coordinator's hands** (withdrawn, the applicant deleted their account, a colleague decided). The decision gets 409 and the screen says "Deze aanmelding is al behandeld." Pinned in Task 4 and Task 12.
4. **Names are not plain ASCII.** The filter finds "Salamanderbrug" for `salamanderbrûg` and `SALAMANDER`, and "Zuid-Oost" for `zuid oost`; a name with markup such as `<b>Noor</b>` is escaped in the HTML part of a mail. Pinned in Task 9 and Task 5.
5. **The ground shifts while the app is open.** A working group is switched off between loading the list and tapping "Meld je aan"; a member is removed while using the app. The app shows a clear text and moves to the right screen without a reload. Pinned in Task 3, Task 8 and Task 11.

- Produces (from `@padvinder/db`):
  - `MEMBERSHIP_REQUESTS_PER_DAY = 5`
  - `type MembershipRequestRecord = { id: string; userId: string; status: MembershipRequestStatus; requestedAt: Date; receivedAt: Date; decidedAt: Date | null; workingGroup: WorkingGroupSummary }`
  - `createMembershipRequest(db: Db, input: { id: string; userId: string; workingGroupId: string; requestedAt: Date; now: Date }): Promise<{ outcome: "created" | "existing"; request: MembershipRequestRecord } | { outcome: "id_in_use" | "working_group_not_found" | "already_member" | "already_requested" | "too_many_requests" }>`
  - `withdrawMembershipRequest(db: Db, input: { id: string; userId: string; now: Date }): Promise<{ outcome: "withdrawn" | "unchanged"; request: MembershipRequestRecord } | { outcome: "not_found" | "already_decided" }>`
  - `getCurrentMembershipRequest(db: Db, userId: string): Promise<MembershipRequestRecord | null>` (the rule of `me.membershipRequest`)
- The order of checks in `createMembershipRequest`, in one transaction:
  1. A row with this `id` exists: the same user gives `existing`; another user gives `id_in_use`.
  2. The working group is missing or not active: `working_group_not_found`.
  3. The user is a member of the group: `already_member`.
  4. The user has a pending request for the group: `already_requested`.
  5. The user created `MEMBERSHIP_REQUESTS_PER_DAY` or more requests in the 24 hours before `now` (by `received_at`): `too_many_requests`.
  6. Insert; `notifyMembershipRequestsChanged` and `notifyAccessChanged`; `created`.

  A primary key or unique index violation from a concurrent insert is caught and the checks run once more, so two simultaneous sends of one `id` give one `created` and one `existing`.

- Withdrawing sets `withdrawn` and `decided_at`, with both events. Withdrawing a withdrawn request is `unchanged`; an approved or rejected one is `already_decided`; someone else's is `not_found`. No audit entry: it is the person's own act.
- Produces (API):
  - `POST /api/membership-requests` (operationId `createMembershipRequest`): 201 `MembershipRequest` for `created`, 200 for `existing`, 404 `not_found`, 409 with the outcome as `code`, 429 `too_many_requests`.
  - `POST /api/membership-requests/{id}/withdraw` (operationId `withdrawMembershipRequest`): 200 `MembershipRequest`, 404, 409 `already_decided`.
  - The route reports `created` to the mail step that Task 5 adds; leave a clearly named hook point (a function `afterMembershipRequestCreated(request)` that does nothing yet).

## Notes from the build (22 November 2026)

- Task 3: `me.membershipRequest` follows the spec, not the plan: the newest pending request; else the newest request if it was rejected; else `null`. The plan's rule (the newest request, if pending or rejected) hid an open request when a newer one for another group had been withdrawn.
- Task 3: creating a request takes a per-user advisory lock, so two requests of one user at the same moment cannot both pass the pending check or the daily limit. An insert that still meets a unique violation (the same ID from another user, committed after the checks) runs the checks once more in a new transaction.
- Task 4: deciding and withdrawing read the request through one query and take the same row lock, so a decision and a withdrawal never both win.
- Task 4: an organization or platform admin may approve their own request; the spec is silent, and admins hold those rights anyway.
- Task 5: the mail to coordinators goes out only while the request is still pending when the mail is built (not after a withdrawal or a deleted account in the meantime). A resend never mails.
- Task 6: `removeMembership` takes the role the caller saw and re-checks it under the row lock; when the member's role changed in the meantime it answers 409 `membership_changed` ("Deze persoon heeft intussen een andere rol. Kijk opnieuw."), a new error code. An admin may remove their own membership: the spec's non-goal concerns members leaving by themselves.
- Task 7: `deleteAccount` takes `lockPlatformAdmins(tx)` before the last-platform-admin check, then the user's request lock, then locks the pending request rows before the user row. The review found that the other order deadlocks with an approval, which locks the request row and then the user row (the membership's foreign key).
- Task 7: for a deleted applicant, `applicant.email` and `applicant.phone` are left out of `MembershipRequestForReview` (both optional), instead of sending an empty address.
- Task 7 (accepted extras): a deleted account has no access, no profile and cannot create requests; the admin tool refuses the replaced address of a deleted account.
- Before Task 4: `recordAudit`'s guard is a case-insensitive substring match on the keys (`name`, `mail`, `phone`), so `fullName` and `emailAddress` are refused too.
- Task 8: `useAccessLiveUpdates` opens the stream again with a capped backoff (2 s, doubling to a minute) after the browser closed it for good, as long as `/api/me` still resolves to a user, because a deploy's 502 closes an `EventSource` for good too. `access-changed` refetches me only when it is for the own user: platform admins receive that event for every user.
- Task 10: `ConfirmDialog` shows a failed action's error inside the dialog, not behind its overlay. Phone numbers become `tel:` links only when they are a plain number (digits, an optional leading `+`, and spaces, hyphens, dots or brackets). A person without a name shows as "Naam niet ingevuld" (and "Deze persoon" in a sentence).
- Task 12: on Leden, members open only in the groups where the user is coordinator or admin (`canOpen` per group); fellow volunteers see names and roles. A list screen opened by URL without any group shows "Dit mag je niet doen.".
