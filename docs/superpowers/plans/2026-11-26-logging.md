# Logging Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One pino logger for the API and the worker, in `packages/logging`, with an allowlist serializer for errors, one `scrub` function for email addresses, quiet health checks, crash handlers and a guide in AGENTS.md (pull request 1 of the logging and monitoring design, issue #3).

**Architecture:** A new shared package exports `createLogger`, `scrub`, `serializeError` and `installCrashHandlers`, plus a test helper. The API passes its logger to Fastify as `loggerInstance` (Fastify keeps an instance's own serializers) and to the notification hub; the worker replaces its `console` logger with it. Every finished JSON line goes through `scrub` in pino's `hooks.streamWrite` (child loggers, Fastify's included, inherit it), so an address never reaches stdout.

**Tech Stack:** pino 10.4.0 (the version Fastify 5.12 already uses), pino-pretty 13.2.0 (development only), Fastify 5, pg-boss 12, Vitest.

**Spec:** `docs/superpowers/specs/2026-11-26-logging-and-monitoring-design.md`, sections "The logger" and "What to log at which level". Sentry is pull requests 2 and 3; nothing here talks to Sentry.

## Global Constraints

- Code, identifiers, comments, tests and docs in English (American spelling); no Dutch text is added in this pull request.
- `LOG_LEVEL` keeps its values `debug`, `info`, `warn`, `error`, default `info`, in both env schemas.
- A runtime dependency of a bundled app is a direct dependency of that app with the same version as in the package that uses it: `pino` `^10.4.0` in `packages/logging`, `apps/api` and `apps/worker`.
- Never in a log line: a name, an email address, a phone number, an IP address, a cookie or header, a login code, a request body or a coordinate. IDs are fine.
- Error serialization is an allowlist: `type`, `message`, `stack`, `code`, `constraint`, `table`, `column`, `cause` (recursively, same rules). Nothing else of an error object.
- `scrub` replaces anything that looks like an email address with `[email]`.
- `/api/health` request lines are not written at `info`; its warnings still are.
- Request lines keep method, URL, status code, response time and `reqId`; never the client's address or port, never headers.
- `pnpm check` passes before the pull request is opened.

## Review Focus

- **An error whose message holds an address** (nodemailer: "could not send to a@b.test", Better Auth): the line holds `[email]`, not the address. Pinned in Task 1 (`serializeError` scrubs `message` and `stack`) and Task 2 (route test).
- **A cyclic value logged** (an error whose `cause` points back at itself, an object that contains itself): logging must not throw or hang. Pinned in Task 1 (`serializeError` cycle test, and a logger test with a cyclic object).
- **A thrown non-Error** (`throw "boom"`, `Promise.reject({ email: "a@b.test" })`): serialized without crashing, scrubbed. Pinned in Task 1 (`serializeError` on a string and a plain object) and Task 1's crash-handler test with a non-Error rejection.
- **An address in a query string** (`GET /api/x?email=a@b.test` from a buggy client): the request line's `url` is scrubbed. Pinned in Task 2.
- **A crash during startup** (before the app exists): the crash handler is installed right after the env is loaded, so the line is still JSON and the exit code 1. Pinned in Task 1's spawn test; Tasks 2 and 3 install it at that point.

**Interfaces:**

- Produces (from `@padvinder/logging`):

  - `type LogLevel = "debug" | "info" | "warn" | "error"`; `const LOG_LEVELS: readonly LogLevel[]` (`["debug", "info", "warn", "error"]`)

  - `serializeError(error: unknown): SerializedError` where `SerializedError = { type: string; message: string; stack?: string; code?: string; constraint?: string; table?: string; column?: string; cause?: SerializedError }`. A non-Error becomes `{ type: typeof value (or "object"), message: scrub(String or JSON of it, at most 500 characters) }`. `cause` follows at most 5 levels and stops on a cycle.
  - `createLogger(options: { service: "api" | "worker"; level: LogLevel; destination?: { write(line: string): void } }): Logger`
  - `installCrashHandlers(logger: Logger, options?: { beforeExit?: () => Promise<void> }): void`
- Produces (from `@padvinder/logging/testing`):
  - `createTestLogger(level?: LogLevel): { logger: Logger; entries(): Array<Record<string, unknown>>; text(): string }` — writes to memory; `entries()` parses each line; default level `debug`.

test("keeps only the allowlisted fields of a PostgreSQL error", () => {
  const error = Object.assign(
    new Error('duplicate key value violates unique constraint "users_email_key"'),
    {
      code: "23505",
      constraint: "users_email_key",
      table: "users",
      detail: "Key (lower(email))=(noor@example.test) already exists.",
      where: "x",
      parameters: ["noor@example.test"],
    },
  );
  const result = serializeError(error);
  expect(result).toMatchObject({
    type: "Error",
    code: "23505",
    constraint: "users_email_key",
    table: "users",
  });
  expect(JSON.stringify(result)).not.toContain("noor@example.test");
  expect(result).not.toHaveProperty("detail");
  expect(result).not.toHaveProperty("parameters");

test("scrubs message and stack, follows cause, stops on a cycle", () => {
  const inner = new Error("smtp refused a@b.test");
  const outer = new Error("send failed", { cause: inner });
  (inner as Error & { cause?: unknown }).cause = outer;
  const result = serializeError(outer);
  expect(result.cause?.message).toBe("smtp refused [email]");
  expect(JSON.stringify(result)).not.toContain("a@b.test");
});
test("a thrown non-Error is serialized and scrubbed", () => {
  expect(serializeError("boom a@b.test")).toEqual({ type: "string", message: "boom [email]" });
  expect(serializeError({ email: "a@b.test" }).message).not.toContain("a@b.test");
});
